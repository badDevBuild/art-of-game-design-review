# 审视路由指南与标准化诊断报告模板

## 一、快速选镜路由表

当不想一次走完 116 张透镜时，按以下两张路由表并用 `scripts/select_lenses.py` 抽取最小高命中透镜组（每次通常 6–15 张）。

### 1. 按研发阶段路由（`--stage`）

| 阶段 ID | 适用时机 | 重点关注的非透镜原则 | 建议连带读取 |
| --- | --- | --- | --- |

## 二、游戏设计审视报告标准模板

每次审视当前游戏时，严格按以下结构交付（事实、推断与试玩假设必须分栏隔离）：

```markdown
# 《{游戏名称}》游戏设计审视报告

- **审视模式**：{工程实景体检 / 阶段门禁 / 症状急诊 / 116 透镜全审}
- **当前阶段与标签**：`{stage}` ｜ `{tags}`
- **本次调用透镜**：`#{id1}`, `#{id2}`, ...（共 N 张）
- **总体裁决**：{继续推进 / 需先修复阻塞项再推进 / 建议暂停并重构核心原型}

## 1. 现状还原与本质体验核对
- **真实游玩场景（Venue）**：{设备、姿势、单局时长、中断频率}
- **核心循环（Core Loop）**：{观察到的最频繁操作闭环，标明来自代码/文档的事实依据}
- **本质体验句**：玩家在 `{场景}` 中感受到 `{核心情绪}`，理解 `{核心规则/世界}`，期待 `{下一步悬念}`，并尝试 `{核心行动}`。
- **核心矛盾（如有）**：{预期体验与现有机制/界面/数值之间的直接冲突}

## 2. 元素四分法（Elemental Tetrad）联动体检
| 要素 | 当前实现（事实） | 是否服务本质体验 | 联动缺口 / 冲突 |
| --- | --- | --- | --- |
| 机制 Mechanics | ... | PASS / WARN / FAIL | ... |
| 故事 Story | ... | PASS / WARN / FAIL | ... |
| 美学 Aesthetics | ... | PASS / WARN / FAIL | ... |
| 技术 Technology | ... | PASS / WARN / FAIL | ... |

## 3. Top 3 致命风险排序
| 排名 | 风险假设 | 致命度(1-5) | 未知度(1-5) | 验证成本(1-5) | 优先级分 | 关联透镜 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 1 | ... | | | | | `#...` |

## 4. 逐透镜与核心原则检查明细
| 透镜 / 原则 | 状态 | 核心发现（标明代码/规则证据） | 最小可落地改进建议 |
| --- | --- | --- | --- |
| Lens #... | PASS / WARN / FAIL / N/A | ... | ... |

## 5. 证据分级表（严禁混淆事实与猜测）
- **已核实事实（来自代码/配置/GDD/实测）**：...
- **设计结构推断（基于机制与规则推导）**：...
- **待真实试玩验证的假设（附通过/失败行为阈值与停止线）**：...

## 6. 下一步最小可证伪行动（限 1–3 项）
1. **{动作名称}**：改动目标 `{文件或规则}`，做 `{最小原型/改动}`，找 `{N 位目标玩家}` 观察 `{具体行为指标}`；若 `{失败行为}` 出现，则执行 `{修改或回退方案}`。
```
